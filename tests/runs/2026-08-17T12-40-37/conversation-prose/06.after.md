Measure before you buy anything. Most test runners report the duration of each test with a flag (`--durations=25`, `--profile`, etc.), so one CI run tells you whether all 900 tests are slow at the same rate or whether 30 of them use half the total time. Each of those two results requires a different fix, and the data you have now does not separate them.

Do not buy the 4-core machine yet. The cost per minute is 2x, so the total cost is equal only if the run becomes twice as fast, and it cannot become twice as fast. The 900 database tests run one after another, so idle cores beside them do not reduce that time. You would pay double to speed up the 300 tests that already run in parallel and are probably not the cause.

Running those 900 tests concurrently is the change most likely to reduce the total time: one schema or database per worker against the same container, so N workers use N isolated namespaces. After that change, extra cores reduce the run time, and the 4-core machine is then worth buying.

You can also try one low-cost change now: run Postgres in CI with `fsync=off` and `synchronous_commit=off`. The container is discarded after the run, so durability has no value in it. The 3.5x difference between local time and CI time is consistent with a slow disk.

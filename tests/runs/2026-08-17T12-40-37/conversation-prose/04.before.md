Three things, one of which is urgent.

**1. SQL injection (blocking)**

`id` comes straight from the path and gets concatenated into the query. `GET /users/1%20OR%201=1` returns the first row in the table — whoever that is — and your caller happily treats it as the authenticated user, `admin` flag and all. Depending on the driver's multi-statement handling, it gets worse than that.

This isn't a "harden it later" item; it's the whole function.

**2. Returns `undefined` on miss, everything else in the file returns `null`**

`db.query` gives back `undefined`, the `if` falls through, and the function ends with no explicit return. Any caller doing `=== null` silently breaks. Make the miss case explicit.

**3. `SELECT *` feeding a three-field projection**

You pull every column, including whatever password/token columns exist, to use three of them. Name the columns — it makes the query self-documenting and stops a future schema addition from leaking through anything that logs `row`.

```js
function getUser(id) {
  const row = db.query(
    "SELECT id, email, is_admin FROM users WHERE id = ?",
    [id]
  );
  if (!row) return null;
  return { id: row.id, email: row.email, admin: row.is_admin === 1 };
}
```

Two smaller notes:

- `is_admin == 1` works but hides what the driver actually hands you. If it's `"1"` or `true`, loose equality papers over it and you'll never know which. Pin the type down and use `===`.
- If `id` should be an integer, reject non-integers at the route boundary rather than letting the DB coerce. Parameterization stops injection; it doesn't stop `/users/abc` from doing something unhelpful.

Measure before you buy anything. Most runners report per-test durations with a flag (`--durations=25`, `--profile`, etc.), so one CI run tells you whether the 900 tests are uniformly slow or whether 30 of them take half the total run time. The two cases need different fixes, and at present you cannot tell which case you have.

Skip the 4-core machine for now. It costs 2x per minute, so it saves money only if the run becomes twice as fast, and it cannot: the 900 database tests run one after another, so the extra cores stay idle. You would pay double to speed up the 300 tests that are already parallel and are probably not the cause.

The largest likely improvement is to run those 900 tests concurrently — a schema or database per worker against the same container, so N workers get N isolated namespaces. With that change, more cores reduce the run time, and the 4-core machine then becomes worth buying.

Try one low-cost change in the meantime: run Postgres in CI with `fsync=off` and `synchronous_commit=off`. The container is discarded after the run, so durability has no value here, and the 3.5x gap between local and CI is consistent with a slow disk.

The SQL injection is urgent. Two other defects follow it.

**1. SQL injection (blocking)**

The function takes `id` from the path and concatenates it into the query. `GET /users/1%20OR%201=1` returns the first row in the table, whoever that row describes. The caller then uses that row as the authenticated user, including the `admin` flag. A driver that runs multiple statements per query allows more than this.

Fix this first. The fix replaces the whole function.

**2. Returns `undefined` on a miss, everything else in the file returns `null`**

`db.query` returns `undefined`, the `if` condition is false, and the function ends with no explicit return. Any caller that tests `=== null` fails without an error. Make the miss case explicit.

**3. `SELECT *` for a three-field projection**

The query selects every column, including any password or token columns, and the code uses three of them. Name the columns. The query then states which columns it reads, and a column added to the schema later does not appear in anything that logs `row`.

```js
function getUser(id) {
  const row = db.query(
    "SELECT id, email, is_admin FROM users WHERE id = ?",
    [id]
  );
  if (!row) return null;
  return { id: row.id, email: row.email, admin: row.is_admin === 1 };
}
```

Two smaller notes:

- `is_admin == 1` works and does not show which type the driver returns. If the value is `"1"` or `true`, loose equality accepts both, and the result does not state which one it was. Determine the type and use `===`.
- If `id` must be an integer, reject non-integers at the route boundary. Don't let the database coerce the value. Parameterization stops injection. It does not stop `/users/abc` from producing an unhelpful result.

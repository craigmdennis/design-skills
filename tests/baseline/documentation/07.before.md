# Bulk Export for the Reporting Dashboard

**Owner (delivery):** Marcus Webb
**Proposed by:** Priya Raman, 2026-04-02
**Scope agreed:** 2026-04-09
**Status:** Approved for first release

## Problem

The reporting dashboard exports one report at a time. A user who wants ten reports runs the export ten times; a user who wants a hundred runs it a hundred times. This is tedious enough that customers write in about it — a support ticket asking for bulk export arrives every week without fail.

The requests are not evenly spread. They come from accounts holding more than 50 reports. That group is about 8 per cent of accounts and about 40 per cent of revenue, so a small share of customers is generating a steady, recurring complaint, and it is the share we can least afford to annoy.

## Solution

Let a user select multiple reports and export them in one action.

Because a large export takes time, the export does not run in the browser. It runs as a background job. When the job finishes, the user receives an email containing a download link. The link expires 24 hours after it is issued.

## Requirements

**Background execution.** The export runs as a background job. The user does not have to keep the dashboard open or wait for the job to complete.

**Email notification.** On completion, the system emails the requesting user a link to the finished export.

**Link expiry.** Download links expire 24 hours after they are issued.

**Format.** The first release supports CSV only.

**Job size limit.** A job covering more than 500 reports is rejected. The rejection message must name the limit explicitly, so the user knows what number to stay under rather than having to guess.

## Out of scope for the first release

Parquet and JSON output. Both are planned for a later release; neither blocks this one.

## Success measure

The weekly count of bulk-export support tickets. Success is that count reaching zero within two months of release.

This is a direct measure rather than a proxy: the tickets are the problem, and their absence is the outcome we want. If tickets continue after two months, the feature has not covered the cases customers actually have, and we should read the remaining tickets before deciding what to build next — the likeliest candidates being the deferred formats or a higher job limit.

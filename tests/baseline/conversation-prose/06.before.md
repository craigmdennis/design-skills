Measure before you buy anything.

The 900 database tests run one after another, so extra cores do almost nothing for them. You'd pay double per minute mainly to speed up the 300 unit tests that are already the fast part. Wrong lever, and you can't tell how wrong until you know where the 14 minutes actually go.

Two cheap things to find out first:

**Per-test timings for the 900.** Most runners emit this already (`--durations`, JUnit XML). One CI run gets you the list. Serial suites usually have a fat tail: a handful of tests doing sleeps, retries, or a full schema reset between cases. If 40 tests own half the time, that's a day's work, not an infra bill.

**Why local is 3.5x faster.** Same tests, same work, so the gap is environment. Image pull, cold caches, container startup, disk, or the Postgres container competing with the test process for two cores. That difference may be worth more than any test-level fix, and it's free to look at.

The likely answer is sharding rather than a bigger machine: split the 900 across a few containers or schemas and run the shards concurrently. Serialized DB tests spend most of their time waiting on I/O, so this helps even on 2 cores, and it costs nothing extra per minute.

Keep the 4-core option on the table but hold it until you have data. At twice the cost per minute it only breaks even if wall clock more than halves, and serialized work won't give you that.

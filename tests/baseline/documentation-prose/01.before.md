Two facts from the list are not in the README below: the author's name, and the date the team agreed to adopt it. The house documentation style in `prompts/documentation-prose.md` bans personal names and decision dates — that history belongs in version control, and it dates the document as soon as ownership changes. The *use* the team agreed on (a pre-push hook) is kept, stated as intended use rather than as a decision record.

```markdown
# shipcheck

shipcheck checks a repository before a push and exits non-zero when a check
fails. It is intended to run in a pre-push hook.

## Install

```
npm install -g shipcheck
```

## Usage

Run it from the root of a repository:

```
shipcheck
```

The checks to run are read from `shipcheck.json` in the current directory.

## Checks

- **No uncommitted changes.** The working tree must be clean.
- **No TODO in staged files.** Staged content must not contain `TODO`.
- **Not on the default branch.** The current branch must be a branch other than
  the default one.

## Options

`--dry-run` prints the checks that would fail and changes nothing.

## Exit codes

`0` when every listed check passes. Non-zero when a listed check fails.

## Pre-push hook

Add the following to `.git/hooks/pre-push` and make the file executable:

```sh
#!/bin/sh
shipcheck
```

A failing check exits non-zero, and the push stops.
```

Three things the facts do not cover, which a reader will look for:

- **The format of `shipcheck.json`.** The README says the file lists the checks, but not how a check is named or enabled. A short example block is the one addition worth making before publishing.
- **What happens when `shipcheck.json` is missing.** Whether that is an error or a no-op changes how safe the hook is to install across repositories.
- **Output on failure.** Whether a failure names the offending files, particularly for the TODO check.
